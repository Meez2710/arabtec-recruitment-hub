## Source findings to reproduce before fixing

- `ScheduleInterviewModal` currently schedules one interview and provides panel-only overlap warnings. Different candidates with different panels are not inherently conflicting. Preserve that ability and the overlapping calendar layout.
- `StandaloneLinkFields` accepts new candidate name/email but no phone or CV. Candidate creation precedes application creation and booking, so a later failure/retry can strand or duplicate records.
- Scheduling automatically calls `notifyEvent('interview.scheduled')`; the form provides no invitation editor/preview or recipient review and ignores the response delivery details in its success toast.
- Interview update and cancellation routes do not dispatch corresponding invitation updates. Confirm all relevant paths before concluding.
- Clash lookup failures are rendered as an empty clash list. There is no candidate conflict check in `findPanelClashes`.
- Phone/WhatsApp sender settings exist, but settings alone do not prove an operational sending integration. Trace existing implementation before changing it.

## Product decisions

1. **Separate appointments:** one interview record per candidate, separate recipients, meeting link/location, panel, status, assessment linkage and communication history. Permit matching start times with disjoint candidates and panels. Add a convenient “Schedule another” action that may retain time/type/duration but clears candidate, CV, recipients and personalized text. No cross-candidate CC, attachments, or copied personal information.
2. **Conflicts:** check candidate and panel overlaps when creating and rescheduling, excluding the current interview. Back-to-back is valid; cancelled/completed/no-show appointments do not occupy future slots. Block the same candidate in overlapping separate appointments. For shared interviewers retain the existing intentional-overlap flexibility, but require a clear acknowledgement and recorded reason before saving. Warn on identical nonempty location/meeting link overlaps; do not pretend arbitrary room text is a reliable resource-booking service. Revalidate at save, handle concurrent requests, and visibly distinguish “availability unavailable” from “no conflict.”
3. **Add candidate without leaving scheduling:** existing-candidate search or new candidate with name, email, international-format phone and CV upload. Reuse candidate duplicate detection and authenticated resume storage, file validation and permissions. Upload is optional, with a clear “No CV attached” state. Let the recruiter resolve a duplicate by selecting the existing record. Failed upload/booking and retries must not create duplicate candidates, applications, interviews or invitations; preserve entered data and the created candidate identifier so the user can continue. Do not rely on AI parsing to permit a manual booking.
4. **CV use:** show the stored CV on interview detail and make it accessible to the assigned panel through existing scoped authorization. Candidate invitation must not contain internal evaluation notes or other candidates' data. Panel invitation should default to an authenticated CV link; allow an explicit attach-CV option only for selected authorized panel recipients, never a shared attachment array copied to the candidate or unrelated recipients. No public CV URLs or broadened Talent Pool visibility. If the current permission architecture cannot safely offer an attachment, retain the authenticated link and document why.
5. **Invitation review:** clear steps/sections for Candidate & CV, Interview details & panel, Invitations. Provide candidate email subject/body and separate panel message preview, recipient list, date/time with explicit timezone, duration, role/request, location or valid meeting link and recruiter contact. Use Africa/Cairo as organization default consistently across UI, stored instants, email and calendar files; retain correct DST conversion. No invented/auto-generated Google Meet link. Validate contact/location/link according to selected channel/mode before sending.
6. **Template setup:** expose a discoverable “Interview invitation templates” entry from Interviews and existing relevant settings. Reuse existing settings/RBAC/notification mechanisms. Authorized recruitment users can edit an individual interview's messages; global reusable defaults remain controlled by existing appropriate settings permission. Support a bounded set of safe placeholders, preview substituted content and reject unresolved/invalid tokens. Do not let template editing grant access to salary/HR-only data or alter sender credentials.
7. **Explicit sending:** distinguish “Save interview” from “Save & send invitations”; avoid automatic sends that bypass preview and selection. Respect global notification switches and report the reason if a chosen channel is disabled/unconfigured. Persist per-recipient/channel attempts and outcomes: not requested, queued, provider accepted, failed; delivered only with real confirmation. Offer retry of failed recipients without replaying successful sends. Prevent double-click/retry duplicate sends with server-side idempotency. Dry-run must be visibly marked as not delivered.
8. **WhatsApp:** provide editable candidate message with international phone validation, Copy message and Open WhatsApp. Opening WhatsApp is a manual handoff, never a sent/delivered status. Do not attach CVs or expose private CV links in external WhatsApp messages. Only expose automatic WhatsApp sending if the existing provider integration is actually implemented/configured and its template/consent requirements can be honored; otherwise clearly label it unavailable and keep the manual route useful. Do not purchase subscriptions, invent credentials or claim provider integration is live.
9. **Changes and cancellations:** provide a visible reschedule/edit action, detect material changes (date, duration, link/location, mode, panel), preview and explicitly send the appropriate update/cancellation. Notify removed panelists appropriately without disclosing new panel-only information. Persist whether changed details were communicated. Calendar UID must remain stable, revisions increase correctly, cancellation is represented truthfully. Do not promise meeting acceptance tracking from a PUBLISH calendar attachment. Preserve history, feedback and application stage.
10. **Workflow controls:** reuse canonical request/application statuses. On-hold, closed/cancelled and terminal applications retain protections. Implement the already-decided Q-05 interview dependency: unapproved requests allow matching but cannot schedule formal interviews. Apply policy consistently to create/reschedule/reactivation paths where relevant without deleting existing history; cancellation must remain possible. Standalone interviews remain supported and can link to a valid application for assessment. Do not introduce a mandatory assessment gate for offers or change unrelated offer policy.
